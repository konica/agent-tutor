# Phoenix Instances Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two separate Arize Phoenix instances ready to receive traces (#288): one on the on-premise host behind Caddy at `https://<domain>/phoenix`, one in the local Compose stack at `http://localhost:10404`. No app service sends to either yet (#289 does).

**Architecture:** On-premise, a `phoenix` Compose service stores traces in a `phoenix` database in the existing Postgres container, made by `deploy.sh`'s role bootstrap from an on-premise-only SQL file. Sign-in is on, with secrets generated by the Host stack. Caddy strips `/phoenix` and proxies to it. Locally, the same image runs without sign-in on SQLite in a named volume. A small `send-test-span.py`, run on the Phoenix image's own Python, proves a span lands in a project in both environments.

**Tech Stack:** Docker Compose, Caddy 2, bash, PostgreSQL 17 (psql), AWS CDK (Python), pytest static tests in `infra/tests/test_host.py` (`cd infra && uv run pytest`).

**Spec:** GitHub issue #288 (parent #286), `sdd/adr/0017-self-hosted-phoenix-for-runtime-tracing.md`.

## Global Constraints

- Image, both environments: `arizephoenix/phoenix:version-20.16.0-nonroot` (published 2026-09-23; user 65532; entrypoint `/usr/bin/python3.13`; no shell, curl, or wget).
- Facts verified against that image (2026-10-12):
  - Phoenix sets the ASGI root path from `PHOENIX_HOST_ROOT_PATH` and expects the proxy to **strip** it. `POST /phoenix/v1/traces` passed through unstripped answers 405; stripped, it is accepted. So Caddy uses `handle_path /phoenix/*`, and services inside Compose post to `http://phoenix:6006/v1/traces`.
  - OTLP/HTTP accepts `application/x-protobuf` only (JSON answers 415).
  - `GET /healthz` answers 200 without a token.
  - `PHOENIX_SECRET` must be ≥ 32 characters with at least one digit and one lowercase letter.
  - `PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD` is not checked against the strong-password policy. The admin must change it at first sign-in.
  - Phoenix creates the default retention policy from `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS` **only when no default policy exists yet** (first start), with a weekly sweep (`0 0 * * 0`).
- On-premise: `PHOENIX_HOST_ROOT_PATH=/phoenix`, `PHOENIX_ENABLE_AUTH=true`, `PHOENIX_ENABLE_STRONG_PASSWORD_POLICY=true`, `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS=180`. The service is on the `default` and `worker` networks, has a read-only root, and runs as non-root. It publishes no port, and gRPC isn't exposed.
- Local: host port **10404** → 6006, no auth, SQLite on the named volume `phoenixdata`, `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS=14`.
- Secrets (Host stack, `smart-tutor-on-premise/...`): `db/phoenix`, `phoenix/secret`, `phoenix/admin-password`, all generated. `phoenix/api-key` is created by the operator (runbook), never by CDK.
- No credential-shaped URL (`scheme://user:pass@host`) anywhere in `deploy/on-premise/` (existing test). Phoenix gets `PHOENIX_POSTGRES_*` variables, not `PHOENIX_SQL_DATABASE_URL`.
- The nightly backup dumps `smart_tutor` and `keycloak` only, never `phoenix`.
- Native-cloud (Helm, `db-bootstrap.sql`) is untouched.
- PRD goes from v2.54 to v2.55 (status line, a "Changes from v2.54" row, §9.12 lists), and `AGENTS.md` cites v2.55.
- Commit subjects in the imperative mood; the body says why. End each commit message with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. `https://<domain>/phoenix` with no trailing slash: it redirects to `/phoenix/`, not to the web app (Task 2 test).
2. A path that only starts with the prefix, such as `/phoenixfoo`, goes to the web app, not Phoenix (Task 2 test: the matcher is `/phoenix/*`, not `/phoenix*`).
3. A generated `PHOENIX_SECRET` without a digit or a lowercase letter would stop Phoenix from starting: `require_each_included_type` (Task 1 test).
4. A redeploy, or a volume restored from a snapshot, reruns the bootstrap. It must be idempotent and reset the `phoenix` role's password to the secret (Task 2: run twice against a real Postgres).
5. The nightly backup never dumps `phoenix` (Task 2 test).

```sql
-- Creates Phoenix's role and database on-premise (#288, ADR 0017), as the container's superuser. deploy.sh pipes it to
-- psql after ../helm/smart-tutor/files/db-bootstrap.sql, in the same session (native-cloud doesn't run Phoenix).
-- Idempotent: every deploy runs it, and it resets the password to the Secrets Manager value, so a rotated secret or a
-- volume restored from a snapshot gets back in sync. The nightly backup leaves this database out (backup.sh).
-- psql variables: phoenix_user, phoenix_password, phoenix_db.
\set ON_ERROR_STOP on
\connect postgres

SELECT format('CREATE ROLE %I LOGIN', :'phoenix_user')
WHERE NOT EXISTS (SELECT FROM pg_roles WHERE rolname = :'phoenix_user') \gexec
ALTER ROLE :"phoenix_user" WITH LOGIN PASSWORD :'phoenix_password';

SELECT format('CREATE DATABASE %I OWNER %I', :'phoenix_db', :'phoenix_user')
WHERE NOT EXISTS (SELECT FROM pg_database WHERE datname = :'phoenix_db') \gexec

-- The role connects only to its own database.
REVOKE CONNECT ON DATABASE :"phoenix_db" FROM PUBLIC;
```
